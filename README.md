# MultiRegistrator Web

**Версия: 1.2.0**

Веб-реализация регистратора данных **MultiRegistrator** на **Django + PostgreSQL**.
Сервис опрашивает устройства по протоколу **Modbus TCP**, сохраняет измерения,
показывает состояние устройств и графики в браузере, ведёт журнал действий
пользователей и предоставляет HTTP API для интеграций.

Проект развивает функционал настольного
[ELJZX/MultiRegistrator](https://github.com/ELJZX/MultiRegistrator) в виде единого
веб-сервиса: сервер опроса, база данных, веб-интерфейс и API работают вместе.

## Что нового в 1.2.0

- График переработан: одна шкала Y с реальными значениями каналов и автоматическим
  подбором «круглых» делений; масштаб Y можно менять вручную без ограничений.
- Свободное панорамирование по времени и по значениям — перетаскиванием с пустого
  места. Нажатие на линию показывает время и значения, подсказка «скользит» по
  графику, не сдвигая его.
- Подписи времени больше не накладываются: количество подписей считается от
  ширины графика, крайние подписи выравниваются внутрь, даты под часами не
  пересекаются.
- Мигающий индикатор «Загрузка данных...» в верхней части графика (над периодом).
- При отдалении графика новые данные не запрашиваются — показывается только уже
  загруженный период.
- Исправлена ошибка `Maximum call stack size exceeded` при открытии больших
  периодов (отчёт за несколько суток).

## Функционал сервиса

### Устройства и опрос
- Список устройств с индикацией состояния: «в сети / недоступно / отключено».
- Настройка устройства: имя, IP/хост, порт, Modbus ID, период опроса, таймаут, повторы.
- Карта каналов: имя, адрес регистра, функция Modbus, тип данных, масштаб, единица
  измерения, порядок слов, флаг записи.
- Поддерживаются `holding`, `input`, `coil`, `discrete`; типы `int16`, `uint16`,
  `int32`, `uint32`, `float32`.
- Фоновый опрос в отдельном процессе `poller`: одно соединение на устройство,
  объединение соседних регистров в минимальное число запросов, без «шторма»
  переподключений.
- Автоматическое определение доступности каналов и последних значений.

### Веб-интерфейс и графики
- Главная страница с карточками устройств и значениями, обновляющимися раз в секунду.
- Страница устройства с графиком Chart.js: период, выбор каналов, автомасштаб,
  сетка, печать/PDF.
- Режим реального времени по умолчанию открывается на **1 минуте** с отступом
  справа 20% для наглядности.
- Масштабирование колесом мыши по обеим осям; перетаскивание с пустого места
  двигает график свободно по времени и по значениям.
- Одна шкала Y с реальными значениями каналов; пока пользователь не масштабировал
  её вручную, диапазон и «круглые» деления автоматически подстраиваются под
  видимые данные.
- Подсказка с временем и значениями каналов появляется при нажатии на линию
  графика; точки показываются только при нажатии.
- Легенда в правом верхнем углу: только видимые каналы, цветные квадраты.
- Ограничения: приближение до 1 секунды, отдаление до 3 суток. При отдалении
  новые данные не запрашиваются: показываются только уже загруженные.
- Ось времени: часовые подписи без секунд, при диапазоне от 2 суток под временем
  показывается дата.
- «Сбросить масштаб» возвращает вид последнего построения: для live — исходное
  минутное окно, для выбранного периода — последний построенный диапазон.
- Адаптивная сетка и защита от переполнения диапазона при сильном отдалении.

### Пользователи и права
- Вход по логину и паролю, страница `/login/`, выход через POST `/logout/`.
- **Администратор** (`is_staff=True`): полный доступ, кнопка «Изменить», кликабельный
  логин в шапке и переход в Django Admin.
- **Пользователь** (`is_staff=False`): только просмотр устройств и графиков;
  логин в шапке некликабельный, кнопка «Изменить» скрыта, `/admin/` недоступен.
- Все страницы устройств и графиков требуют авторизации; API остаётся доступным
  для интеграций в режиме чтения.

### Администрирование и сканирование каналов
- Управление устройствами, каналами и пользователями в Django Admin.
- **Поиск Modbus ID**: перебор диапазона ID и запись найденного значения в устройство.
- **Сканирование каналов**: чтение holding/input-регистров и поиск правдоподобных
  `float32`-каналов (big/little word order) с текущими значениями.
- Найденные каналы можно отметить, задать имена и добавить в устройство одной кнопкой.
- Журнал действий пользователей доступен в админке.

### Хранение и журналирование
- Измерения сохраняются в PostgreSQL и/или CSV-архиве (`database`, `files`, `both`).
- Журнал действий `devices_usereventlog`: просмотры страниц, формирование графиков,
  печать/PDF, вход, выход, неудачные попытки входа.
- Для события пишутся пользователь, IP, браузер, путь, метод, длительность,
  HTTP-статус и детали (период, каналы, количество точек).
- Live-обновления графика в журнал не пишутся, чтобы не засорять его.
- Изменения в админке дополнительно фиксируются в `django_admin_log`.

### API и Docker
- HTTP API для списка устройств, последних значений, каналов, дат и данных за период.
- Docker-развёртывание: PostgreSQL, web (Django + Gunicorn), poller и демо-профиль
  с эмулятором устройства.
- Версионированные Docker-образы: `multiregistrator-web:1.2.0`.

## Архитектура

```
multiregistrator_web/   настройки Django
devices/                приложение: модели, Modbus, опрос, API, веб-интерфейс
  management/commands/  poll_devices, test_device, seed_demo
  templates/devices/    страницы, вход и общие шаблоны
  static/devices/       стили и логика графиков (Chart.js, chart-utils.js)
  tests/                Django-тесты и JS-тесты
archive/                CSV-архив (если ARCHIVE_STORAGE=files|both)
```

В Docker поднимаются отдельные сервисы:

- `db` — PostgreSQL 16;
- `web` — Django + Gunicorn (веб-интерфейс и API);
- `poller` — отдельный процесс `python manage.py poll_devices` (фоновый опрос);
  пишет heartbeat, по которому `poller_health` проверяет, что опрос действительно
  идёт;
- `testdevice` и `seed-demo` — опциональный демо-профиль с эмулятором.

Опрос вынесен в отдельный процесс, чтобы веб-сервер мог работать в несколько
воркеров, а устройства опрашивались ровно один раз.

## Быстрый старт в Docker

```bash
docker compose up -d --build
```

Интерфейс: http://localhost:8080/  
Вход: http://localhost:8080/login/  
Админка: http://localhost:8080/admin/  
API: http://localhost:8080/api/health

Создать администратора:

```bash
docker compose exec web python manage.py createsuperuser
```

### Сборка на другой машине

Все файлы для сборки (`Dockerfile`, `docker-compose.yml`, `.dockerignore`,
`requirements.txt`) хранятся в репозитории, поэтому контейнер собирается из
исходников на любой машине с Docker:

```bash
git clone https://github.com/ELJZX/MultiRegistratorWeb.git
cd MultiRegistratorWeb
cp .env.example .env      # необязательно: порты, пароли, часовой пояс
docker compose up -d --build
```

С демо-устройством (эмулятор Modbus):

```bash
docker compose --profile demo up -d --build
```

В Windows PowerShell вместо `cp` используйте `Copy-Item .env.example .env`.
Без `.env` compose запустится на значениях по умолчанию.

Версия образа задаётся переменной `APP_VERSION` (по умолчанию `1.2.0`):

```bash
APP_VERSION=1.2.0 docker compose up -d --build
```

### Production на одной VM

`docker-compose.prod.yml` — отдельный стек для production: тянет готовый образ
из registry, не собирает его на сервере, запускает миграции один раз через
one-shot сервис `migrate` и не публикует PostgreSQL наружу.

Заполните `.env`:

- `APP_IMAGE` — репозиторий образа без тега, например
  `ghcr.io/eljzx/multiregistrator-web`;
- `APP_VERSION` — версия/тег образа;
- `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `POSTGRES_DB`, `POSTGRES_USER`,
  `POSTGRES_PASSWORD` — обязательные значения без небезопасных дефолтов.

Запуск:

```bash
docker compose -f docker-compose.prod.yml --env-file .env pull
docker compose -f docker-compose.prod.yml --env-file .env up -d
curl http://localhost:8080/api/ready
```

Для staging на той же VM используйте отдельные `COMPOSE_PROJECT_NAME`,
`WEB_PORT` и `.env`; контейнеры и volumes будут разделены по имени проекта.

### Пользователи и права

- **Администратор** — учётная запись с флагом `is_staff` (суперпользователь получает
  все права). В шапке сайта логин кликабельный и ведёт в Django Admin; доступны
  редактирование устройств и каналов и полный функционал.
- **Пользователь** — обычная учётная запись без `is_staff`. Может войти на сайт и
  просматривать список устройств и графики, но не видит кнопку «Изменить», не имеет
  доступа к `/admin/`, а логин в шапке отображается как обычный некликабельный текст.

Пользователи создаются в `/admin/auth/user/`. Для администратора включите
«Staff status» (при необходимости — «Superuser status»); для обычного пользователя
оставьте «Staff status» выключенным.

## Демо без реального оборудования

Запустить эмулятор устройства и добавить его в базу:

```bash
docker compose --profile demo up -d testdevice
docker compose run --rm web python manage.py seed_demo --host testdevice --port 5020
```

После этого на странице http://localhost:8080/ появится «Демо-устройство»,
а сервис `poller` начнёт писать показания (температура, влажность, счётчик, реле).
Через несколько секунд данные появятся на графике устройства.

## Добавление устройства и сканирование каналов

1. Откройте `/admin/devices/device/add/`.
2. Укажите имя, IP/хост, порт и (при необходимости) Modbus ID.
3. Сохраните устройство.
4. На странице устройства нажмите **«Поиск и сканирование каналов»** (внизу формы)
   или **«Сканировать»** в списке устройств.
5. При необходимости найдите Modbus ID, затем выполните сканирование holding/input
   регистров. Отметьте найденные каналы, задайте имена и добавьте их.

Сканирование ищет `float32`-каналы, как в оригинальном проекте. Каналы других типов
добавляются вручную в таблице каналов.

## Управление графиком

- Live-режим открывается на 1 минуте и обновляется раз в секунду; подпись
  «Обновлено:» статична, меняется только время.
- Колесо мыши масштабирует обе оси; перетаскивание с пустого места — свободное
  панорамирование по времени и по значениям.
- Нажатие на линию показывает время и значения; пока кнопка нажата и мышь
  движется, подсказка скользит по графику, а сам график не смещается.
- Шкала Y одна (реальные значения каналов). Пока её не масштабировали вручную,
  минимум, максимум и шаг подписей автоматически подстраиваются под видимые
  данные. Ручной масштаб по Y ничем не ограничен и сбрасывается кнопкой
  «Сбросить масштаб» или повторным включением live-режима.
- При нажатии на линию показываются время и значения каналов; точки видны только
  при нажатой кнопке мыши.
- Легенда показывает только видимые каналы, в правом верхнем углу.
- Ограничения: минимум 1 секунда, максимум 3 суток (или шире, если отчёт
  изначально построен за больший период). При отдалении данные не подгружаются
  автоматически: видно только то, что уже загружено для выбранного периода.
- Ось времени: при часовом шаге подписи без секунд; от 2 суток под временем
  выводится дата.
- «Сбросить масштаб» возвращает к последнему построенному виду: live-окно или
  выбранный диапазон.
- «Сформировать график» строит отчёт за выбранный период и отключает live.
- «Печать / PDF» открывает печатную версию A4 в альбомной ориентации без служебных
  надписей и адреса страницы.

Карточки устройств на главной странице также обновляют значения раз в секунду.

## Хранение данных

Режим задаётся переменной `ARCHIVE_STORAGE`:

| Значение | Поведение |
| --- | --- |
| `database` | только PostgreSQL (по умолчанию) |
| `files` | только CSV-файлы в `archive/<host>/<host>_<дата>.txt` |
| `both` | CSV-файлы + PostgreSQL |

CSV-формат совместим с оригинальным проектом:

```
archive/
    192.168.1.10/
        192.168.1.10_2026-11-09.txt
```

```
timestamp,temperature,humidity
2026-11-09 12:00:00.123,25.4,55.0
```

## Журнал данных и действий

- показания устройств сохраняются в PostgreSQL в таблицу `devices_measurement`
  при `ARCHIVE_STORAGE=database` или `both`;
- действия пользователей сохраняются в таблицу `devices_usereventlog`:
  просмотры страниц, формирование графиков, печать/PDF, вход, выход и неудачные
  попытки входа;
- для каждого события пишутся пользователь, IP-адрес, браузер, путь, метод,
  длительность, HTTP-статус и детали (период, каналы, количество точек);
- live-обновления графика в журнал не пишутся, чтобы не засорять его;
- изменения в административной панели Django дополнительно фиксируются в
  стандартной таблице `django_admin_log`;
- журнал действий доступен в админке: «Журнал действий пользователей».

## HTTP API

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/api/health` | liveness: процесс отвечает, версия |
| GET | `/api/ready` | readiness: процесс и подключение к БД |
| GET | `/api/info` | информация о приложении |
| GET | `/api/devices` | список устройств и их состояние |
| GET | `/api/devices/{id}` | одно устройство (по id или host) |
| GET | `/api/devices/{id}/latest` | последние считанные значения |
| GET | `/api/devices/{id}/channels` | список каналов |
| GET | `/api/devices/{id}/dates` | доступные даты архива |
| GET | `/api/devices/{id}/data?start=&end=&channels=` | данные за период |
| POST | `/api/log/print` | журналирование печати/PDF (используется интерфейсом) |

`start` и `end` — ISO-дата/время. `channels` — имена каналов через запятую.

## Тесты

Django-тесты:

```bash
python manage.py test
```

JS-тесты расчётов графика (нужен Node.js 18+):

```bash
npm run test:js
# или
node --test devices/tests/js/chart-utils.test.js
```

Django-тесты покрывают декодирование регистров, объединение запросов, модели,
хранение, опрос, API, эмулятор, журнал действий и права пользователей.
JS-тесты покрывают ограничения масштабирования, привязку к данным, шаг сетки,
«круглые» деления оси Y, прореживание подписей и сброс к базовому виду.

## CI

GitHub Actions workflow `.github/workflows/ci.yml` запускается на push в `main` и
на pull request:

- Django-тесты на SQLite и PostgreSQL;
- JS-тесты графика;
- проверка, что изменения моделей закоммичены вместе с миграциями;
- сборка Docker-образа и smoke-тест compose-стека с PostgreSQL.

Секреты для CI не требуются. Smoke-тест собирает образ с тегом `ci`, проверяет
`/api/health`, `/api/ready` и `/api/info`, после чего удаляет контейнеры и volumes.

## CD и выкладка

- `main` -> production: после успешного `CI` workflow `Main deploy` собирает
  образ с тегом `sha-<short>` и сразу обновляет `multiregistratorweb` на 8010.
- Тег `vX.Y.Z` -> release: проверка версии и тестов, публикация образа в GHCR,
  smoke-тест и выкладка production.
- Перед миграциями `deploy.ps1` делает `pg_dump`; при неудачном healthcheck
  автоматически возвращает предыдущую версию.

Production рассчитан на self-hosted GitHub Actions runner на Windows-хосте
с Docker Desktop (Linux containers); отдельная VM и SSH не нужны. Staging
отключён, production обновляется автоматически после каждого успешного CI на
`main`. Подробная настройка окружений, секретов, runner, бэкапов и отката — в

## Версионирование и Docker-образы

- Версия сервиса задаётся `APP_VERSION` (по умолчанию `1.2.0`) и возвращается
  API `/api/health`, `/api/ready` и `/api/info`.
- Docker-образы тегируются версией: `multiregistrator-web:${APP_VERSION}`.
- В образ добавляется метка `org.opencontainers.image.version`.
- Релиз сопровождается git-тегом `v1.2.0`.

## Отличия от настольной версии

- Клиент и сервер объединены в веб-приложение; графики строятся в браузере
  (Chart.js), печать/PDF — через печать браузера.
- Вместо JSON-файлов конфигурации устройства хранятся в БД и редактируются в
  Django Admin.
- Добавлены авторизация и роли, журнал действий, сканирование каналов,
  отдельный процесс опроса, PostgreSQL-хранилище и Docker-развёртывание.

## Планы

- Запись регистров (write) из интерфейса.
- Экспорт отчётов и дополнительные форматы архива.
- Несколько источников данных и расширенная визуализация.
